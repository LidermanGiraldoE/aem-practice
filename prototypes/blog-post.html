Cómo pensar un bloque antes de escribir una sola línea de código

El modelo de contenido es el contrato entre autores y desarrolladores. Este es el proceso que usamos para diseñar bloques que se editan a la primera.

LG Liderman GiraldoFrontend · AEM
20 oct 2026 · 12 min de lectura
content → model → block

En resumen

  • Empieza por el contenido real, no por el diseño ni por el JSON del modelo.
  • Cada campo del modelo debe tener un nombre que el autor entienda sin ayuda.
  • Las variantes visuales van en classes, no en bloques duplicados.

Casi todos los bloques difíciles de mantener tienen el mismo origen: se diseñaron desde el código hacia el contenido. Alguien vio un Figma, escribió el JavaScript y al final inventó un modelo para que “encajara”. El resultado es un formulario lleno de campos que el autor no entiende.

En Edge Delivery Services el orden correcto es el inverso. Y no es una preferencia: el markup que entrega AEM depende directamente de cómo modelas los campos.

1. Contenido primero

Antes de abrir el editor, escribe el contenido real que va a llevar el bloque. No “Lorem ipsum”: textos reales, con su longitud real. Te vas a dar cuenta rápido de qué es obligatorio, qué es opcional y qué se repite.

  • ¿Se repite? Entonces es un bloque contenedor con ítems.
  • ¿Cambia solo el aspecto? Es una variante, no un bloque nuevo.
  • ¿Es una lista de datos? Quizá vive mejor en un Content Fragment.
✓
Regla prácticaSi no puedes explicar el bloque con un ejemplo de contenido real en una frase, todavía no está listo para programarse.

2. Diseña el modelo para el autor

El modelo es la interfaz del autor. Los nombres de los campos y sus descripciones son copy de producto, no detalles técnicos.

_feature-card.json
{
  "id": "feature-card",
  "fields": [
    { "component": "text", "name": "title", "label": "Title" },
    { "component": "richtext", "name": "text", "label": "Description" },
    { "component": "aem-content", "name": "link", "label": "Link" }
  ]
}

Nombres que se explican solos

Evita text1, text2 o field_a. Usa los sufijos de field collapse (Alt, Text, Type, Title) para que AEM agrupe la imagen con su texto alternativo o el enlace con su etiqueta.

“Un buen modelo de contenido se nota cuando el autor no necesita abrir la documentación.” — Equipo de Experiencia Digital

3. Variantes, no copias

Si dos bloques comparten estructura y solo cambian colores, alineación o columnas, son el mismo bloque con variantes. Así mantienes un único JavaScript y un único modelo.

¿Bloque nuevo o variante?

Cuidado con los nombres de claseLas variantes se convierten en clases CSS. Evita nombres que choquen con utilidades de Tailwind como table, block o hidden.

4. Decora sin romper el contrato

El JavaScript del bloque recibe un DOM predecible. Léelo, transfórmalo y conserva la instrumentación de Universal Editor para que el autor siga pudiendo seleccionar cada ítem.

feature-cards.js
export default function decorate(block) {
  // cada fila es una tarjeta; las vacías se conservan para UE
  const items = [...block.children].map((row) => ({
    title: row.querySelector('h3')?.textContent || '',
    href: row.querySelector('a')?.href || '',
  }));
  render(items, block);
}

5. Checklist antes del pull request

  1. El bloque funciona con campos vacíos u opcionales.
  2. Los encabezados respetan la jerarquía de la página.
  3. Todo es accesible con teclado y tiene nombres accesibles.
  4. Probaste en móvil, tablet y escritorio, en tema claro y oscuro.
  5. npm run lint pasa sin errores.

Diseñar desde el contenido parece más lento al principio, pero cada bloque que modelas bien es un bloque que nadie tendrá que reescribir. Si quieres practicarlo, sigue la guía Crea tu primer bloque.
